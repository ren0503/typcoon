# Data Model: 002-business-modules

Authoritative column-level definitions live in `docs/schema.sql` and are delivered verbatim by migration `00002_business_schema.sql` (FR-010). This document records the **business view**: module ownership, entity purpose, validation rules, operations, and cross-entity rules that the service layer must enforce. Column types/defaults are not duplicated here except where services must reason about them.

## Conventions (apply to every module)

- **Identity**: UUID v7 generated by the application before insert (FR-017); `gen_random_uuid()` DB default is a fallback only. Exceptions per schema: `audit_log.id` is `bigint IDENTITY`, `change_log(ship_id, seq)` / `ops_events(hub_id, local_seq)` / `ship_seq(ship_id)` are composite or non-UUID keys (FR-016).
- **Common columns** on synced tables: `id`, `created_at`, `updated_at`, `version`, `deleted_at`; `updated_at`/`version` are trigger-maintained and MUST NOT be written by application logic (FR-018).
- **Status enums** are `text` + `CHECK` constraints; each accepted value is a validated application constant in the owning module (FR-019). Any value outside the constraint fails with a validation error before reaching the DB wherever the service knows the enumeration.
- **Soft delete**: tables with `deleted_at` support soft delete only; normal reads exclude deleted rows; a soft-deleted parent is as good as a missing parent (Clarification 2026-11-02: uniform rejection).
- **Timestamps** are timestamptz; `date` columns are date-only; `time` columns are time-of-day (`end_time < start_time` means overnight for shift templates and is legal).
- **Uniqueness after soft delete**: `voyages(ship_id, code)`, `ships.imo_number`, `ports.un_locode` remain unique even for soft-deleted rows (schema observation; services surface a distinct conflict error and reuse stays blocked until a future schema decision).
- **Page size**: default 20, max 100, clamped (FR-039). List operations below support cursor pagination unless noted "internal".

## Module `tenant`

| Entity (table) | Purpose | Validation / rules | Initial operations |
|---|---|---|---|
| Tenant (`tenants`) | Root customer organization | `name` required; email/name uniqueness N/A; no cross-tenant access | Create, get, list, update, soft delete |

No references depend on `tenants` beyond FK ownership checks. Creating a tenant yields `id` and timestamps only (database-managed fields excluded from request/response).

## Module `ship`

| Entity (table) | Purpose | Validation / rules | Initial operations |
|---|---|---|---|
| Ship (`ships`) | Vessel master data | `tenant_id` required; `imo_number` unique even after soft delete; `timezone` non-empty IANA zone name validated in service; status enum active/maintenance/retired | Create, get, list, update, soft delete |
| Deck (`decks`) | Structural level | `level` int; unique `(ship_id, level)` among non-deleted | Create, get, list, update, soft delete |
| Area (`areas`) | Common area on a deck | `area_type` enum; `deck_id` must reference an existing, non-deleted deck of the same ship; `layout` is JSONB (shape not enforced this phase) | Create, get, list, update, soft delete |
| Room (`rooms`) | Bookable cabin/crew room | `room_type` enum; `capacity` > 0; unique `(ship_id, number)` among non-deleted; `is_bookable` default true; layout JSONB | Create, get, list, update, soft delete |

Parent-reference rule: `deck_id` on areas/rooms must resolve to a non-soft-deleted deck belonging to the same `ship_id`; otherwise 422 validation. Soft-deleting a ship with active decks/rooms is allowed at the DB level but the service requires non-deleted children resolution per the uniform rule (children simply become invalid for new references — no cascade deletion this phase).

## Module `voyage`

| Entity (table) | Purpose | Validation / rules | Initial operations |
|---|---|---|---|
| Port (`ports`) | Global reference data (no ship/tenant scope) | `un_locode` unique even after soft delete; `country_code` 2-char; lat/long numeric(9,6) optional | Create, get, list, update, soft delete |
| Voyage (`voyages`) | Sailing window | `arrival_at > departure_at` (DB CHECK + service); overlap prevention by `ex_voyages_no_overlap` EXCLUDE constraint for non-cancelled/non-deleted; `code` unique per ship (even after soft delete); `status` enum planned/prepared/boarding/sailing/completed/cancelled; `ownership` cloud/ship is read-only metadata (rows created this phase are `cloud`); `schedule_version` is workflow-managed by later features and not exposed to basic updates | Create, get, list, update, soft delete |
| Port call (`port_calls`) | Itinerary stop | `sequence >= 1` unique per voyage among non-deleted; `port_id` of existing non-deleted port; eta/etd/ata/atd optional timestamps; `allows_embark/disembark` booleans; status enum scheduled/arrived/departed/skipped | Create, get, list, update, soft delete |

State transitions: none automated this phase (FR-036). Statuses are plain constrained values; `ownership` is always `cloud` for rows created here.

## Module `partner`

|---|---|---|---|

## Module `booking`

| Entity (table) | Purpose | Validation / rules | Initial operations |
|---|---|---|---|
| Booking (`bookings`) | Reservation of a room for a voyage | parents resolve (ship, voyage, optional account, optional room); `disembark_seq > embark_seq` (DB CHECK + service); room-overlap exclusion `ex_bookings_room_no_overlap` for pending/confirmed/checked_in active rows — DB is the final authority; status enum pending/confirmed/checked_in/checked_out/cancelled/expired; **status is immutable via API this phase** (Clarification 2026-11-02): update covers `special_requests`, `room_id`, `embark_seq`/`disembark_seq`, `expires_at` family fields only; `expires_at` optional (pending hold); `source` cloud/ship metadata; `idempotency_key` unique with account per partial index | Create (with `Idempotency-Key` semantics, R10), get, list, update basic fields, soft delete. Audited (FR-057) |
| Service booking (`service_bookings`) | Purchase of a partner service within a booking | parents resolve (booking, partner_service, optional slot/guest); `quantity > 0`; status enum pending/confirmed/rejected/cancelled/completed; **status may be updated directly** to allowed CHECK values (Clarification 2026-11-02); `idempotency_key` unique with booking | Create (idempotent), get, list, update basic status, soft delete. Audited (FR-057) |

Booking lifecycle orchestration (waitlists, upgrades, checkout flows, payment) is out of scope (FR-036).

| Entity (table) | Purpose | Validation / rules | Initial operations |
|---|---|---|---|

## Cross-module relationships (read dependencies, one direction each)

```text
partner ──uses──▶ ship (validate ship scope)
booking ──uses──▶ voyage, ship, partner (validate parents), guest (reference check only)
guest   ──uses──▶ booking (parent resolution), auth (account existence)
booking/guest/staff ──emit──▶ audit (Appender, same tx)
all software modules ──emit──▶ audit (deferred except the three above)
```

No cycles: each arrow is a one-way interface dependency; composition root wires them (FR-007/008).
